# P0-3 触发中心（Triggers）落地方案

> 目标：把 my-cowork 目前割裂的「skill 定时 job（`/api/schedule/jobs`）」与「飞书 webhook」统一为 **eigent 式 Trigger 系统**：schedule / webhook / slack 三类触发器统一 CRUD + 启停 + 执行记录 + 活动日志 + 实时事件。
> **对齐基准：eigent Trigger 实现**（本方案每个功能点都标注对应 eigent 源码文件，实现时逐条对照，保持一致）。

## 1. 目标与非目标

### 1.1 目标
- 统一触发器模型：`schedule` / `webhook` / `slack_trigger`（与 eigent TriggerType 一致；my-cowork 本期实现 schedule + webhook，slack 预留）。
- 完整 CRUD + 启用/停用 + 复制 + 排序（对齐 eigent TriggerDialog/Triggers/TriggerListItem）。
- 执行记录：`pending → running → completed/failed/cancelled/missed`，含 tokens_used/duration/error/retry（对齐 eigent ExecutionStatus + ExecutionLogs）。
- 活动日志：创建/更新/删除/启用/停用/执行/成功/失败/取消 全量入 activityLog（对齐 eigent activityLogStore）。
- 调度语义：cron 表达式 + 一次性（date）+ 过期日期 + 每时/每日执行上限 + 连续失败自动停用（对齐 eigent schedule service）。
- Webhook：`POST/GET /webhook/trigger/{uuid}`，限流 + app handler 鉴权 + URL 校验挑战 + `pending_verification → active` 状态流转（对齐 eigent webhook_controller）。
- 实时事件：执行创建/更新/触发激活 实时推到客户端（对齐 eigent WS 协议，SSE 传输）。

### 1.2 非目标
- Slack 真实接入（只做类型/UI 预留，与 eigent 一致保留 slack_trigger 形态）。
- 失败 replan / 自动重试策略（仅保留手动 retry，同 eigent `proxyRetryTriggerExecution`）。
- 触发器与 space/project 深度绑定（my-cowork 本期只存 `space_id/project_id` 字段，绑定后续做）。

## 3. 数据模型（对齐 eigent `trigger.py` / `trigger_execution.py`）

SQLite 单库 `~/.my-cowork/triggers.db`：

```sql
CREATE TABLE triggers (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id        TEXT NOT NULL DEFAULT 'local',
  space_id       TEXT,                          -- 预留
  project_id     TEXT,                          -- 预留
  name           TEXT NOT NULL,
  description    TEXT NOT NULL DEFAULT '',
  trigger_type   TEXT NOT NULL,                 -- 'schedule' | 'webhook' | 'slack_trigger'
  status         TEXT NOT NULL DEFAULT 'inactive', -- eigent TriggerStatus
  webhook_url    TEXT,                          -- 自动生成 /webhook/trigger/{uuid}
  webhook_method TEXT,                          -- 'GET' | 'POST'
  custom_cron_expression TEXT,
  listener_type  TEXT NOT NULL DEFAULT 'workforce',
  agent_model    TEXT,                          -- 预留（channel 默认模型体系打通后使用）
  task_prompt    TEXT,
  config         TEXT,                          -- JSON（按 config_registry 校验）
  max_executions_per_hour INTEGER,
  max_executions_per_day  INTEGER,
  is_single_execution     INTEGER NOT NULL DEFAULT 0,
  last_executed_at        INTEGER,
  next_run_at             INTEGER,
  last_execution_status   TEXT,
  consecutive_failures    INTEGER NOT NULL DEFAULT 0,
  auto_disabled_at        INTEGER,
  created_at              INTEGER NOT NULL,
  updated_at              INTEGER NOT NULL
);

CREATE TABLE trigger_executions (
  id              TEXT PRIMARY KEY,             -- execution_id
  trigger_id      INTEGER NOT NULL,
  status          TEXT NOT NULL,                -- eigent ExecutionStatus
  execution_type  TEXT NOT NULL,                -- 'scheduled' | 'webhook' | 'slack'
  input_data      TEXT,                         -- JSON
  task_id         TEXT,                         -- my-cowork TaskManager task_id
  started_at      INTEGER,
  completed_at    INTEGER,
  duration_seconds REAL,
  output_data     TEXT,
  error_message   TEXT,
  skip_reason     TEXT,
  attempts        INTEGER NOT NULL DEFAULT 0,
  tokens_used     INTEGER NOT NULL DEFAULT 0,
  tools_executed  TEXT,
  created_at      INTEGER NOT NULL,
  updated_at      INTEGER NOT NULL
);
```

**枚举（严格对齐 eigent）**：
- `TriggerType = schedule | webhook | slack_trigger`
- `TriggerStatus = inactive | active | pending_verification`
- `ExecutionStatus = pending | running | completed | failed | cancelled | missed`
- `ExecutionType = scheduled | webhook | slack`
- `ListenerType = workforce`

## 6. 调度服务（对齐 eigent `trigger_schedule_service.py`）

- **计算 next_run**：`croniter(expr, base)` 取下一次（一次性 `date` → DateTrigger 语义）。
- **到期轮询**：APScheduler 新增一个 30~60s 的 interval job（对齐 eigent Celery beat `fetch_due_schedules`）：查 `status=active AND trigger_type=schedule AND next_run_at <= now`，逐条 `dispatch`。
- **dispatch 前置检查**（对齐 eigent）：
  1. `_check_schedule_valid`：过期日期已过 → 停用并置 `auto_disabled_at`；
  2. `check_rate_limits`（max_executions_per_hour/day，用 executions 表统计）；
  3. `is_single_execution`：已执行过则不再触发；
  4. 计算下次 `next_run_at` 并落库。
- **执行**：创建 `TriggerExecution(status=pending, execution_type=scheduled)` → `TaskManager.handle(TaskRequest(text=task_prompt, source="trigger:schedule", ...))` → 监听 `graph.end` 更新 execution（completed/failed/cancelled + duration + 摘要），tokens_used 从 `metrics` 或 `graph.end` usage 取。
- **连续失败自动停用**：`consecutive_failures >= max_failure_count`（config）→ `status=inactive` + `auto_disabled_at`（对齐 eigent 字段）。
- **missed**：轮询间隔内应跑未跑（next_run_at 严重过期且未执行）→ 标 `missed`。

## 7. Webhook 服务（对齐 eigent `webhook_controller.py`）

```
POST|GET /webhook/trigger/{uuid}
  1. 限流：10 次/60s（对齐 eigent RateLimiter）
  2. body 解析：JSON 失败则 {"raw_body": ...}；headers 透传
  3. 按 uuid 查 trigger（type ∈ {webhook, slack_trigger}，status ∈ {active, pending_verification}）
  4. app_handler = get_app_handler(trigger_type)
     ├─ handler.authenticate(request, body, trigger) → 失败 401
     ├─ URL 校验挑战（如 Slack challenge）→ 直接返回 challenge（状态不变）
     └─ 真实事件且验签通过：
         ├─ status=pending_verification → active（对齐 eigent 首次真实事件激活）
         ├─ 创建 TriggerExecution(status=pending, execution_type=webhook, input_data={method,query,body,headers(过滤敏感头)})
         ├─ 提交流程同 §6（source="trigger:webhook"）
         └─ 推 trigger_activated / execution_created 事件
```

- `app_handler_service.py`（对齐 eigent）：注册表 `get_app_handler(trigger_type)`；my-cowork 本期实现 `WebhookAppHandler`（通用，无签名要求），预留 `SlackAppHandler`（验签 + challenge）；后续可把 `webhook_lark` 收敛为 `LarkAppHandler`。

## 8. 实时事件（SSE 替代 WS，消息体对齐 eigent）

`GET /api/trigger/stream`（EventSource）：
- 连接即发 `connected`（含 session_id/timestamp）。
- 心跳：服务端每 30s 发 `heartbeat`；客户端每 2min 发 ping（fetch `POST /api/trigger/ping`），服务端回 `pong`（对齐 eigent PING_INTERVAL/PONG_TIMEOUT 语义，SSE 单向由服务端推）。
- 事件（字段与 eigent `useExecutionSubscription` 接口逐字段一致）：
  - `execution_created`：`{execution_id, trigger_id, trigger_type, status, execution_type, input_data, project_id, timestamp, task_prompt?}`
  - `execution_updated`：`{execution_id, trigger_id, status, updated_fields[], project_id, timestamp, task_prompt?}`
  - `trigger_activated`：`{trigger_id, trigger_type, webhook_uuid}`
- 断线：客户端重连后全量 `GET /api/trigger` 兜底（对齐 eigent 重连 + 查询失效逻辑）。

## 11. 分阶段实施与验收

### Phase 1（schedule 触发器闭环）
1. `models/store/config_registry/schedule/executor/manager`
2. 路由 CRUD + activate/deactivate + executions + config schema
3. 前端 `TriggerPanel/TriggerDialog/SchedulePicker/DynamicTriggerConfig/TriggerListItem/Triggers`
4. 验收（对齐 eigent 核心行为）：
   - [ ] 创建一次性/每日/每周/每月触发器 → 列表出现、状态 inactive
   - [ ] 启用后 `next_run_at` 正确；到点执行 → `execution_created → running → completed`，结果落 executions
   - [ ] cron 非法/过期日期 → 前端校验拦截；config schema 由 `/api/trigger/schedule/config` 驱动
   - [ ] 连续失败 ≥ max_failure_count → 自动停用（auto_disabled_at 落库）
   - [ ] 复制/编辑/删除/启停 全流程；按创建时间/上次执行排序
   - [ ] 单测：`fetch_due_schedules`、限流、missed、一次性不重复触发

### Phase 2（webhook 触发器 + 实时事件）
1. `trigger_webhook.py` + app_handler 注册表 + 限流 + URL 校验
2. SSE `/api/trigger/stream` + `useTriggerStream` + `useTriggerTaskExecutor`
3. `ExecutionLogs` + retry + 活动日志联动（`activityLog` 随 execution 状态更新）
4. 验收：

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| 后端是子进程，重启丢失内存态 | 全部状态落 `triggers.db`；重启后 APScheduler 重新注册轮询 job，`next_run_at` 从库恢复（对齐 eigent SQL 持久化） |
| 轮询粒度（30-60s）与 cron 秒级冲突 | 与 eigent 一致接受分钟级调度；`missed` 语义处理延迟触发 |
| SSE 心跳/断线 | 客户端 `heartbeat` 30s 判定 + 重连全量拉取（对齐 eigent unhealthy 判定） |
| 执行与任务状态不同步 | `trigger_executions.task_id` 关联 `TaskManager`；`graph.end` 订阅回写（含 cancelled） |
| 与 SkillScheduler 双轨 | 明确职责：skill 声明 schedule → SkillScheduler；用户自由创建 → TriggerManager；UI 分区展示 |
| 长 prompt 撑爆输入 | `task_prompt` 上限 1500 字符（对齐 eigent），webhook body 截断 8KB |
