# 开发规范

本页承接[开发计划](../历史/开发计划.md)原“全局规则”，作为这些规则的现行维护位置。历史里程碑仍留在原文中；这里没有宣布旧里程碑已重新验收通过。

## 原有五条规则

1. **先想后写**：任务开始前在任务记录里复述假设；如发现文档没有明确的细节，先澄清，不直接选定实现方案。
2. **从简**：实现以满足验收为边界；不增加验收之外的字段或方法。
3. **小范围改动**：只修改任务声明的模块；不顺手重构未列出的部分。
4. **检查分层**：新增后端子包后运行 `lint-imports`；规则定义见 [backend/.importlinter](../../backend/.importlinter)，装配入口为 `app.main`。
5. **TDD**：行为修改先写能暴露问题的失败测试，再实现并验证。文档整理检查引用、事实与差异，不把文档检查称为功能测试通过。

执行命令统一维护在[开发指南](开发指南.md)。这里不复制命令或某台机器的失败数量。

## UI/UX 开发流程

本项目长期执行，适用于涉及用户操作的功能。顺序：**作用范围 → 入口位置 → 操作过程 → 视觉设计 → 实际验收**。

1. **先定归属与入口。** 明确功能影响全局、某个插件、项目、对话还是本次任务，以及用户何时需要它；当前操作就近放在工作界面，全局默认放在设置。例如，本次提问的思考强度放在输入区附近，新对话的默认值可放在设置。
2. **先走通操作过程。** 明确从哪里进入、经过哪些步骤、结果在哪里，以及如何返回、取消和处理失败；减少重复输入和无意义切换。小改动沿用既有模式，复杂新流程先补简短说明或必要草图，记录放在当前任务文档。
3. **保持简约清晰。** 优先沿用现有布局、组件和交互习惯，突出主操作与必要信息；减少无意义的 Logo、图标、装饰和重复提示，保留用户做决定所需的信息。
4. **随功能一起实现和验收。** 同步完成界面、状态反馈和操作逻辑。交付前实际走完使用过程并检查真实界面，确认入口易找、影响范围清楚、步骤合理、结果可找回；影响使用的问题在本段收尾前解决。

## 完成时留下什么

改动说明应能回答：之前是什么问题、现在有什么行为、为什么这样改、如何验证、还有什么未验证。

- **实现状态**与**验证状态**分开。存在实现或测试文件，不等于运行通过。
- 验证记录注明代码版本或未提交工作区、系统、命令、结果及未覆盖范围。用户手工实测与自动测试分别记录。
- 原有失败应与相同环境下的基线对照，记录具体失败项；不能只比较失败总数。
- 提交、PR、合并分别记录，不把“已实现”写成“已交付”。

## 文档怎么维护

| 信息 | 维护位置 |
|---|---|
| 阅读顺序、文档状态 | [文档索引](../README.md) |
| 当前模块与代码入口 | [当前架构](当前架构.md) |
| 开发和验证命令 | [开发指南](开发指南.md) |
| 原计划与实现差异、历史选择的依据 | [旧方案与当前实现对照](旧方案与当前实现对照.md)，引用原文 |
| 单个功能的详细行为 | 对应专题，如[定时任务实现](定时任务实现.md) |

同一事实只在一个主位置维护，其他文档链接过去。代码与运行结果说明“现在如何”，已确认的需求和验收说明“应该如何”；两者不一致时记录差异，不自动认定哪一方正确。历史材料中的外部产品能力、价格和版本是当时记录，重新选型时应重新核实。
