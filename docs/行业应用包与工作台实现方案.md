# 行业应用包与工作台实现方案

状态：首批实现已落地，后续能力按本文阶段继续实施。目标平台：当前项目的 Electron + React + FastAPI 桌面应用。

当前已实现：可信 ZIP 的清单/校验/安装、单进程 Python 路由注册、工作台页面容器、专用静态协议、受限业务 API 桥接、行业应用路由的 Electron 主进程令牌认证、任务管理样例、手动回退与停用。macOS 的 PyInstaller 成品已验证能加载包外 Python 模块，并确认无令牌访问被拒绝、带令牌业务路由可用；Electron 隐藏窗口已验证样例页面资源与桥接消息。

当前未实现：全局本地 API 认证与 CORS 收紧、Windows 成品验证、AI 工具与 Skills 注册、数据迁移、签名、自动故障回退和通用第三方 Python 依赖。这些能力的清单声明在当前安装器中会被拒绝，防止静默失效。

## 1. 结论与边界

行业应用是可安装的本地业务模块，可以包含 Python 业务逻辑、完整页面、数据库迁移、AI 工具和 Skills。MyCowork 保持一个 Electron 主进程和一个现有的 Python 后端进程；多个行业应用注册到同一个 FastAPI 进程，不为每个应用启动 Python 服务。

首版接受用户信任的本地 ZIP。进程内 Python 能访问宿主进程的内存、环境变量和文件权限，因此清单中的权限只能约束宿主提供的 API，不能构成恶意 Python 代码的安全沙箱。开放第三方应用市场前，需要另行决定审核与隔离机制；“任意不可信 Python ZIP”和“全部运行在同一 Python 进程”无法同时获得强隔离。

首版采用两种应用类型：

| 类型 | 内容 | 示例 |
| --- | --- | --- |
| workflow | 清单、Skills、表单/任务模板，可无 Python 和独立页面 | 行业公文助手 |
| python-web | Python 模块、构建后的静态页面、可选 Skills、迁移 | 任务管理、轻量 ERP |

本文以 python-web 为完整样例。workflow 复用同一安装与工作台入口，跳过 Python 和页面注册。

## 2. 当前代码约束

- electron/python_runner.ts 已启动并监管一个 FastAPI 后端。开发模式走 uv，打包模式走 PyInstaller 可执行文件。
- backend/app/main.py 的 create_app() 集中装配依赖和 APIRouter，适合接入应用注册器。
- backend/app/skills/config.py 的 ZIP 导入只面向 Skills，直接解压并替换目录，不能复用为可执行应用安装器。
- renderer/src/components/hub/HubView.tsx 与 renderer/src/store/pageTab.ts 已提供主页标签结构，可以加入工作台与应用页面状态。
- electron/main.ts 的 localfile 协议启用了 bypassCSP，只用于现有预览，不承载行业应用页面。
- backend/app/main.py 当前 CORS 允许全部来源；backend/app/server/localhost_only.py 仅检查本机来源。应用页面上线前要为普通 API 增加身份认证并收紧 CORS。

## 3. 总体结构

    ZIP 文件
      │ 校验、预演、安装
      ▼
    应用注册表 ── 版本目录 ── 独立数据目录
      │                │
      │ 启用后重启     ├─ Python 模块 → 现有 FastAPI 进程
      │                └─ 前端 dist → mycowork-app:// 应用来源
      ▼
    工作台 React 外壳 → iframe 应用页面 → 受控桥接 → Electron 主进程
                                                     │ 带宿主认证
                                                     ▼
                                              /api/apps/{id}/...

React 外壳负责应用列表、标签、返回、加载与错误提示；业务页面由应用自己构建。Python 插件提供业务 API 和可选 AI 工具。页面通过桥接调用该应用的 API，不接触通用 Electron preload 或后端地址。

## 4. ZIP 规范 v1

文件扩展名为 .zip；根目录必须直接包含 mycowork-app.yaml，不增加任意外层文件夹。路径区分大小写，统一使用正斜杠和 UTF-8 文件名。相同路径、绝对路径、父目录跳转、符号链接和设备文件均拒绝。

    taskboard-1.0.0.zip
    ├── mycowork-app.yaml
    ├── checksums.sha256
    ├── backend/
    │   └── mcapp_cn_example_taskboard/
    │       ├── __init__.py
    │       ├── plugin.py
    │       ├── api.py
    │       ├── store.py
    │       └── migrations.py
    ├── frontend/
    │   └── dist/
    │       ├── index.html
    │       └── assets/...
    ├── skills/
    │   └── taskboard/SKILL.md
    └── assets/
        └── icon.svg

清单样例：

    schema_version: 1
    id: cn.example.taskboard
    name: 任务管理
    version: 1.0.0
    description: 本地任务与项目看板
    min_host_version: 0.0.9
    sdk_version: 1
    kind: python-web
    platforms: [darwin-arm64, darwin-x64, win-x64]
    backend:
      entry: mcapp_cn_example_taskboard.plugin:register
      requires_python: ">=3.11,<3.13"
    ui:
      entry: frontend/dist/index.html
      route_mode: hash
      bridge_version: 1
      min_width: 720
    data:
      scope: workspace
      migration_entry: mcapp_cn_example_taskboard.migrations:migrate
    capabilities:
      host_api: [files.pick, ai.start_task, notifications.show]
      network_domains: []
    skills:
      - skills/taskboard

清单字段采用严格 schema 校验，未知字段在 v1 中报错。id 使用反向域名格式，安装后不可改名；version 使用 SemVer。Python 顶层包名固定为 mcapp_ 加规范化后的 id，防止不同应用模块名冲突。entry 只能指向 backend/ 内的该包，ui.entry 只能指向 frontend/dist/ 内文件。包应包含打包好的 JS/CSS，不在安装时执行 npm、pip 或任意 postinstall 脚本。

checksums.sha256 覆盖除自身之外的所有包内文件，检测损坏与安装过程中的内容变化。它本身不证明发布者身份；后续签名应覆盖清单与校验表。首版无签名包必须由用户在安装预览中明确选择信任。

### Python 依赖政策

v1 允许 Python 标准库和版本化的 MyCowork App SDK；FastAPI、Pydantic 等宿主共享依赖只通过 SDK 明确开放的接口使用。ZIP 不安装任意第三方包，不允许携带 native 扩展。前端依赖在开发时自行构建并打进 dist，运行时无 npm 依赖安装。

这样可以在单个解释器中避免不同应用争用同名包的版本。轻量 ERP 和任务系统的首版可使用 sqlite3、SDK 和静态前端。后续若要支持额外 Python 依赖，需要设计经审核的共享依赖目录与兼容矩阵；不能给每个进程内插件建立虚拟环境并假定其依赖相互隔离。

当前 PyInstaller 产物加载包外 Python 源文件的能力，必须分别在 macOS 和 Windows 成品中做验收。若无法可靠加载，先把后端打包方式调整为随桌面端分发版本固定的可扩展 Python 运行时，再开放 ZIP 中的 Python 入口。开发模式成功不算通过此门槛。

## 5. 后端嵌入契约

新增 app/industry_apps/ 子系统：manifest、installer、registry、loader、sdk、routes、data、migrations。应用注册器在 create_app() 装配期间读取“已启用版本”，验证并导入 Python 入口。每个入口遵守固定签名：

    def register(context: AppContext) -> AppContribution:
        return AppContribution(
            router=router,
            tools=[create_task_tool, list_overdue_tool],
            jobs=[],
        )

注册时的 AppContext 提供 app_id、日志、工作空间数据目录解析器及经声明的宿主服务接口；具体 workspace_id 从每次请求或任务上下文取得。AppContribution 由宿主注册；应用的 APIRouter 统一加上 /api/apps/{id} 前缀，路由名和 AI 工具名加 id 命名空间。应用不能直接修改全局 FastAPI app、任务注册表或其他应用的数据目录。这个契约有助于兼容和排错，但对可信进程内 Python 不是强制沙箱。

应用可定义启动与停止钩子，但由主 FastAPI lifespan 显式调用；不依赖挂载子应用的 lifespan。注册应轻量，数据库连接或大对象可在首次请求时初始化。同步耗时业务代码应通过宿主提供的线程执行入口运行，避免阻塞事件循环；插件仍须遵守资源预算。

建议宿主接口：

| 接口 | 用途 |
| --- | --- |
| GET /api/apps | 已安装应用、版本、启用状态、页面入口 |
| POST /api/apps/install/inspect | 只校验 ZIP，返回清单、包哈希、权限、冲突与升级影响 |
| POST /api/apps/install/commit | 校验包哈希与 inspect 一致后安装，记录待重启版本 |
| POST /api/apps/{id}/enable | 标记启用，提示后端重启 |
| POST /api/apps/{id}/disable | 标记停用，提示后端重启 |
| DELETE /api/apps/{id} | 卸载程序；数据保留或删除由用户选择 |
| /api/apps/{id}/... | 插件业务路由 |

安装和版本切换由应用注册表管理，不在运行中的 FastAPI 上热插拔路由。启用、停用和升级都在当前任务结束后重启现有后端进程；工作台在重启期间展示状态并恢复原应用标签。

## 6. 前端页面嵌入

### 工作台信息结构

在 Hub 顶级导航增加“工作台”。工作台首页展示已安装应用与行业分类，提供安装 ZIP、更新、停用和打开入口。打开后进入应用标签，保留宿主顶栏与返回工作台操作。应用内部的二级导航和业务表单由应用负责；宿主只保存 app_id、当前路径、标签标题和草稿离开提示。

每次只挂载当前应用的 iframe；切换应用时保存其内部路由，返回时重建页面，避免大量后台页面常驻。应用需要通过自身持久化保存未提交草稿，或通过桥接声明“离开前提示”。页面有加载中、资源缺失、后端未就绪、应用已停用四种明确状态。键盘焦点进入和离开 iframe 后仍能访问宿主导航。

### 静态资源协议

Electron 注册独立的 mycowork-app 协议，页面地址形如：

    mycowork-app://cn.example.taskboard/index.html

域名部分就是 app_id，因此不同应用拥有不同来源。协议仅映射该应用当前已启用版本的 frontend/dist，校验路径归属，拒绝目录遍历；只提供静态文件，不代理通用后端 API。注册为标准、安全协议，保留 CSP 检查，不启用 bypassCSP。页面禁止远程脚本、Node 集成、任意新窗口和未经授权的导航。应用页面不加载现有 electron/preload.ts。

初版使用 iframe，并通过独立来源与 sandbox 属性限制页面能力。若未来有需要独立崩溃恢复或复杂窗口控制的重型页面，可再评估 WebContentsView；它不会增加 Python 服务进程。现有预览用的 webview 与 localfile 协议不复用。

### 页面桥接 v1

应用前端 SDK 提供有限方法：

    host.app.request({ path: "/tasks", method: "GET" })
    host.files.pick()
    host.ai.startTask({ prompt: "..." })
    host.navigation.setRoute("#/projects/42")
    host.ui.setDirty(true)

实现为 iframe 与宿主 React 页面之间的 postMessage 请求/响应；宿主逐条校验 event.source、event.origin、app_id、桥接版本、操作名和参数 schema，然后调用 Electron IPC。Electron 主进程再次校验消息来自宿主窗口，只把该应用命名空间内的 API 请求转发给后端。应用页面永远不收到后端地址或宿主认证令牌。开发和成品测试均须确认自定义协议的 origin 值符合预期；若无法稳定识别，页面通信改由独立 WebContentsView 的 IPC 发送方身份校验承载。

主题、语言和窗口尺寸由宿主通过桥接发事件，应用 SDK 设置 CSS 变量。提供一份基础设计令牌和可选 React 组件包，保证表格、表单、空状态和错误状态风格一致；应用仍可自行实现页面。应用内部路由使用 hash 模式，刷新时不要求静态协议处理服务端路由回退。

## 7. 本地 API 与安全前置工作

当前“仅监听 localhost + CORS *”无法阻止同机网页或应用页面调用其他业务 API。引入应用页面前：

1. Electron 启动后端时生成每次启动唯一的随机令牌；后端对非 /health、非已有签名 webhook 的 API 校验令牌。
2. 宿主 React 的现有 fetch、SSE 等调用迁移到统一 API client，由 Electron 主进程代理；代理须保留流式响应能力。随机令牌仅保存在 Electron 主进程与 Python 后端，行业应用 iframe 不接触令牌。
3. 生产环境移除全来源 CORS；开发环境确需跨来源直连时，只允许明确的本地开发来源。验证 Host 与 Origin；不要把 CORS 当作认证。
4. 应用协议响应设置严格 CSP，限制脚本、资源、连接、表单和顶层导航；IPC 按调用方窗口及方法白名单校验。
5. ZIP 安装前限制压缩包大小、展开总大小、单文件大小、文件数、压缩比；拒绝路径跳转、重复路径、链接和可执行安装钩子。

上述措施隔离页面 JS 和普通本机 HTTP 调用。进程内 Python 仍按可信代码处理，签名和用户确认解决来源与知情问题，不提供恶意代码沙箱。

## 8. 安装、更新和数据生命周期

安装状态：未安装 → 校验中 → 待确认 → 已暂存 → 待重启 → 已启用；失败时进入“安装失败”并保留旧版本。

安装器先读取 ZIP 中的清单和文件表，不执行代码；在临时目录逐项校验后解包，检查版本、SDK、平台、资源路径与权限差异，向用户展示影响。inspect 返回包哈希，commit 再校验同一包的哈希，防止确认后文件被替换。用户确认后写入不可变的版本目录，更新注册表中的待激活版本。重启后加载并做应用健康检查，成功才切换 active_version；失败恢复旧版本并记录诊断。注册表用数据库记录版本指针，避免 Windows 符号链接差异。

建议目录：

    ~/.my-cowork/industry-apps/packages/{app_id}/{version}/
    ~/.my-cowork/industry-apps/data/{app_id}/{workspace_id}/
    ~/.my-cowork/industry-apps/registry.db

业务数据永远不写入版本目录。每个应用和工作空间有独立 SQLite 数据库。升级前备份数据；迁移记录版本号并在可行时使用事务。迁移失败即回退程序与数据备份。卸载默认保留数据，另提供明确的“连同数据删除”。反复启动失败时进入安全模式，暂停最近激活的应用；用户可从工作台查看日志、回滚或停用。

## 9. 开发者工作流与样例

新增开发工具，命令名称为拟定：

    mycowork-app init taskboard
    mycowork-app dev ./taskboard
    mycowork-app validate ./taskboard
    mycowork-app pack ./taskboard

init 生成 Python 入口、React/Vite 页面、清单和 SQLite 迁移模板。dev 将目录作为可信开发应用挂到现有后端，Vite 提供页面热更新；pack 构建静态资源、生成校验表和 ZIP。validate 使用与安装器相同的清单和路径规则。

仓库内建立 examples/taskboard：项目与任务 CRUD、看板页、SQLite 迁移、两个 AI 工具和一个 Skill。它同时是开发文档、端到端验收包与跨平台打包烟雾测试对象。

## 10. 实施顺序与验收

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| P0 运行时与认证 | 成品中动态加载纯 Python 样例；统一 API 认证和 CORS；确定 PyInstaller 是否可继续使用 | macOS、Windows 安装包都能加载 ZIP 代码；无令牌请求被拒绝 |
| P1 后端插件底座 | 清单 schema、安装器、注册表、SDK、路由与迁移生命周期 | 安装/升级/失败回滚/卸载样例包不丢数据 |
| P2 页面容器 | 工作台入口、应用标签、专用协议、iframe、桥接和主题 | 页面可打开、导航、调用自身 API；无法调用未授权宿主方法 |
| P3 参考应用 | 任务管理应用与开发工具 | ZIP 在干净机器安装后可增删改查、重启持久化、AI 创建任务 |
| P4 产品化 | 签名、诊断、安全模式、兼容矩阵、开发文档 | 安装器拒绝无效包；可检测的加载失败有原因且可回退 |

必要测试包括：ZIP 路径跳转、压缩炸弹、重复条目、伪造清单、跨应用资源访问；伪造 postMessage、跨应用 API 调用、无令牌直连本地端口；升级中断、迁移失败、应用导入异常；至少 10 个已安装应用的启动与页面切换。测试应覆盖开发模式与 macOS/Windows 成品。
