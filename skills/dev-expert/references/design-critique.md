# 设计评审与认知负荷（Design Critique & Cognitive Load）

> **定位**：前端 / UI 交付前的设计评审闸门——用 **10 透镜系统走查** + **尼尔森启发式评分卡** + **认知负荷审计** + **UX 文案规范**，把"好不好用"从主观感受变成可定位、可分级、可验收的问题清单。与 `frontend-design` 第七步（可访问性、安全性与可用性检查）协同，复杂页面 / 关键流程 / 上线前视觉走查时加载。
> **触发**："评审"、"critique"、"设计打分"、"启发式评估"、"认知负荷"、"界面文案"、"UX 写作"、"按钮文案"、"可用性审计"、"设计走查"、"这个页面哪里怪"、"帮我挑毛病"。
> **铁律**：**评审是只读活动，先出分级问题清单，不默认重写设计**；**每条问题必须可定位（位置）、可复现（现象）、可验收（判定标准）**；**存在未决 P0 / P1 问题时不得宣称"设计通过"**。

## 第一部分：设计评审（Design Critique）

### 第一步：评审准备

- 明确评审对象：页面 / 组件 / 流程 / 文案，附目标用户与核心任务
- 确定评审维度：10 透镜走查 + 尼尔森启发式评分卡 + 认知负荷审计
- 只读原则：不改设计稿、不写代码，审计结论确认后才进入修复（呼应 SKILL.md「审计修复分离」）

### 第二步：10 透镜逐项走查

对每个透镜输出 ✅ / ❌ / 部分，❌ 必须附位置与现象：

| # | 透镜 | 检查要点 |
| - | ---- | -------- |
| 1 | 第一印象 | 3 秒内能否看出"这是什么页面、能做什么、下一步去哪"；首屏是否聚焦单一目标 |
| 2 | 品牌一致性 | 色彩 / 字体 / 间距 / 圆角 / 阴影 / 图标语言是否统一；有无风格漂移或拼贴感 |
| 3 | 信息层级 | 标题 / 正文 / 辅助信息层级清楚；最重要的操作在视觉上是否最突出；无"处处强调 = 处处不强调" |
| 4 | 布局 | 间距节奏、对齐、栅格一致；无拥挤、失衡、意外空白；留白本身是设计而非缺陷 |
| 5 | 空状态 | 无数据 / 无结果 / 初始状态是否有说明 + 引导 + CTA，而非空白或"暂无"敷衍 |
| 6 | 反馈 | 点击 / 提交 / 保存是否有即时反馈；成功与失败提示是否明确；错误信息是否可行动 |
| 7 | 可点击性与信任 | 可点击元素看起来可点击（禁用态可辨识）；无欺骗性 UI（假按钮 / 诱导勾选）；安全敏感操作有确认与撤销路径 |
| 8 | 可访问性 | 对比度 WCAG AA；键盘可达、焦点可见、Esc 关闭浮层；图片有 alt；动效可降级 |
| 9 | 移动与响应式 | 关键路径小屏可完成；触控热区 ≥44px；断点无溢出、无横向滚动（数据表格除外） |
| 10 | AI 痕迹检测 | 模板感 / 通用感 / 假内容 / 重复句式 / 占位文案（Lorem、TODO） / "千篇一律的 4 卡布局"；宏观结构须与同项目其他页面不同 |

| # | 启发式 | 评分 | 关键发现 |
| - | ------------------------------------------------ | ---- | -------- |
| 1 | 系统状态可见性 | | |
| 2 | 系统与现实世界匹配 | | |
| 3 | 用户控制与自由（撤销 / 重做 / 退出） | | |
| 4 | 一致性与标准 | | |
| 5 | 错误预防 | | |
| 6 | 识别而非回忆 | | |
| 7 | 灵活高效（快捷键 / 默认值 / 批量） | | |
| 8 | 美学与极简设计 | | |
| 9 | 帮助用户识别、诊断、从错误恢复 | | |
| 10 | 帮助文档与引导 | | |

- 平均分 < 7 或任一核心路径启发式 ≤ 5 → 该页面不得宣称"设计通过"
- 打分必须附一句"为什么"，禁止只给数字

### 第四步：严重度分级与问题清单

| 级别 | 定义 | 处置 |
| ---- | ------------------------------------------ | ---------------------- |
| P0 | 阻断核心任务 / 数据风险 / 误导性操作 | 上线前必须修复 |
| P1 | 核心路径受阻 / 明显误导 / 一致性破坏 | 本轮迭代修复 |
| P2 | 体验受损 / 效率下降 / 次要一致性问题 | 排期修复 |
| P3 | 打磨项 / 风格偏好 | 收集后统一处理 |

问题清单格式（每条必须三要素齐全）：

```
| 问题 | 位置（页面/组件/步骤） | 严重度 | 依据（透镜/启发式/认知负荷项） | 建议 |
```

### 第五步：问题排序与行动计划

- 按 严重度 × 影响面 排序：P0 > P1 且影响核心路径者最先
- 每个 P0 / P1 问题落到具体修复动作 + 验收方式（改后走第几步复查）
- P2 / P3 进迭代池，不阻塞交付；但必须显式记录，禁止"先不管"静默丢弃

## 第二部分：认知负荷（Cognitive Load）

### 第一步：认知负荷三分法

| 类型 | 含义 | 评审目标 |
| ---- | -------------------------------------------- | -------- |
| 内在负荷 | 任务本身固有的复杂度（无法消除） | 拆步骤，别堆一屏 |
| 外在负荷 | 界面呈现方式额外强加的负担（可优化） | 降低，是评审主战场 |
| 相关负荷 | 用户理解、学习、建立心智模型的投入 | 用平实语言与一致性引导 |

### 第二步：四项工作记忆上限

- 一次呈现的概念 ≤ 4 个（工作记忆约 4±1）
- 首屏决策点 ≤ 3 个；表单字段按场景分组，单屏 ≤ 7 项
- 单个页面主 CTA 唯一；同级操作 ≤ 7 个（超出用"更多"收纳）
- 步骤条 ≤ 5 步；超长流程必须分步 + 进度提示（呼应 `api-design.md` 长任务 Init→Step→Poll 的前端呈现）

### 第三步：认知负荷审计 8 项

1. 是否要求用户记住上一步内容？（应"识别而非回忆"，关键信息就地呈现）
2. 术语是否与用户心智一致？（专业黑话 / 内部缩写 / 技术名词面向终端用户 = 负荷）
3. 是否存在多余点击 / 输入？（每多一步都消耗负荷；默认值、预填、智能猜测优先）
4. 是否提供默认值与合理预填？（表单、筛选、排序给默认，用户只需改例外）
5. 信息密度是否过高？（每屏焦点是否单一；次要信息可折叠 / 渐进披露）
6. 出错后是否保留已填内容？（页面刷新 / 校验失败不得清空表单）
7. 是否避免模式切换？（列表 ↔ 表单、详情 ↔ 编辑之间来回跳 = 高负荷，考虑行内编辑 / 抽屉）
8. 文案是否平实？（见第三部分；长句拆短句，术语首次出现给解释）

### 第四步：过载模式识别与缓解

| 过载模式 | 症状 | 缓解 |
| -------- | ------------------------------------ | ------------------------------ |
| 向导轰炸 | 一步问太多问题 | 分步、每步 ≤ 4 个概念 |
| 表单马拉松 | 字段过多未分组 | 分组 + 进度提示 + 默认值 |
| 术语墙 | 通篇专业术语 / 黑话 | 用户语言改写，glossary 兜底 |
| 选择瘫痪 | 选项过多无推荐 | 默认推荐 + 渐进披露高级项 |
| 信息洪流 | 首屏塞满 | 焦点单一化，次要内容折叠 |

## 第三部分：UX 文案（UX Writing）

### 第一步：按钮与操作文案

- 动词开头、结果导向："保存草稿"、"提交订单"、"删除文件"；禁止裸"确定 / 提交 / OK"
- 主操作用具体动词；次要 / 取消保持中性，不与主操作并列抢视觉
- 危险操作按钮写明后果："删除" → "删除文件"（+ 确认弹窗说明不可恢复）

### 第二步：错误信息

- 结构：问题是什么 + 为什么 + 怎么办（三步缺一即不合格）
- 不指责用户："你输入错误" → "这个格式暂不支持，请使用 11 位手机号"
- 给出下一步：重试 / 修改建议 / 联系支持；保留已填内容

### 第三步：空状态

- 结构：这里是什么 + 为什么为空 + 下一步能做什么
- 必须给 CTA，禁止纯占位文案（"暂无数据"后要跟"去创建"）

### 第四步：术语与一致性

- 同一概念全站同一叫法（维护 glossary）；禁止"订单 / 单据 / 工单"混用
- 面向终端用户不用内部黑话（"驳回" → "退回修改"视受众而定）
- 数字 / 日期 / 单位 / 币种格式全站统一
