# 事故复盘与 SLO（Incident Review & SLO）

> **定位**：覆盖线上事故的两类工程活动——**事故复盘**（事后追溯根因、行动项闭环、避免甩锅）与 **SLO / 错误预算**（用可量化的服务目标管理可靠性，把"系统稳不稳"变成可度量、可告警、可决策的数据）。生产事故、线上故障、可靠性治理、告警策略讨论时加载。
> **触发**："事故复盘"、"线上故障"、"incident"、"SLO"、"错误预算"、"error budget"、"可用性 99.9%"、"告警阈值"、"燃烧率"、"burn rate"。
> **铁律**：**复盘不甩锅（blameless）**；**SLO 是业务决策不是纯技术数字**；**未落行动项的复盘 = 未完成**。

## 第一部分：事故复盘

### 第一步：建立时间线

按时间顺序还原事故全程，所有时间标注来源（监控 / 日志 / 值班记录）：

```
## 时间线
- T-30min: [最后正常状态 / 最近一次成功发布]
- T0:      [首个异常信号：哪条告警 / 哪个用户反馈 / 哪个指标拐点]
- T+5min:  [发现与初步响应]
- T+30min: [定位到根因 / 临时止血]
- T+2h:    [恢复 / 验证]
```

时间线的作用：区分**发现延迟**与**恢复延迟**，分别找原因——发现慢是监控 / 告警问题，恢复慢是预案 / 定位问题。

### 第二步：影响评估

- 影响范围：受影响的用户 / 功能 / 数据
- 影响时长：从 T0 到恢复
- 严重度分级：S1（核心功能不可用）/ S2（部分功能受损）/ S3（轻微降级）
- 是否违反 SLO / 消耗错误预算（见第二部分）

### 第三步：根因分析（复用根因调试硬闭环）

- 复用 `root-cause-debugging.md` 的假设列表 + 反向追溯 + 根因 vs 补丁判定门禁
- **5 Whys 追问**：每个根因继续追问"为什么"，直到到达可执行的改进项（如"发布未走灰度"→ 为什么没走 → 发布流程没有灰度门槛）
- **区分根因 / 触发因素 / 放大因素**：根因是修复对象，触发因素是这次为何发生，放大因素是为何影响这么大（如无冗余、无降级开关）

### 第四步：行动项闭环（不甩锅原则）

- 每条行动项格式：`[动作] + [负责人/角色] + [截止时间] + [验证方式]`
- 行动项分三类：**修复类**（根因修复）、**防护类**（防止同类：监控、告警、预案、发布门禁）、**复盘类**（流程改进）
- 复盘会结束后必须有人跟进行动项，下次复盘先过上次行动项状态
- 语言要求：谈论"系统 / 流程 / 工具"缺陷，不谈论"谁的失误"；个人失误也转化为流程 / 工具改进

### 第五步：复盘报告模板

```
## 事故复盘报告

**事故编号 / 标题**：[ID] - [一句话]
**严重度**：S1/S2/S3
**时间线**：[见上表，含发现延迟与恢复延迟分析]
**影响**：[范围 / 时长 / 用户与数据影响 / SLO 影响]
**根因**：[根因 + 触发因素 + 放大因素]
**证据**：[监控截图 / 日志 / 时间线数据]
**行动项**：[修复类 / 防护类 / 复盘类，含负责人、截止、验证]
**预防措施**：[同类事故的流程 / 工具改进]
**遗留**：[未验证项 / 未决问题]
```

## 第二部分：SLO 与错误预算

### 第一步：定义 SLI（服务指标）

SLI 必须可采集、可计算，常见示例：

| 维度 | SLI 示例 |
| ---- | -------- |
| 可用性 | 有效请求成功率（非 5xx / 总请求） |
| 延迟 | P50 / P95 / P99 在阈值内的请求占比 |
| 吞吐 | 每分钟处理请求数 / 消息数 |
| 数据新鲜度 | 最近一次成功同步时间与当前时间差 |
| 持久性 | 成功写入且未丢失的比例 |

SLI 定义必须明确**分母**（哪些请求计入）与**窗口**（滚动 28 天 / 30 天 / 季度）。

### 第二步：设定 SLO（服务目标）

- SLO 是**业务决策**：与用户期望、商业承诺、成本平衡后设定，不是拍脑袋的 99.99%
- 建议设定在"够用且留有余量"的水平：如用户承诺 99.9%，SLO 可定 99.95%（留错误预算应对事故）
- 分级：核心路径（高 SLO）与边缘功能（低 SLO）分开设，避免一刀切

### 第三步：错误预算（Error Budget）

```
错误预算 = 1 - SLO
消耗 = 窗口内实际不可用时间 / 窗口总时间
剩余 = 错误预算 - 消耗
```

- 错误预算耗尽 → 停止发布新功能，优先做可靠性工作（这是 SLO 的核心治理价值）
- 消耗速度用**燃烧率**监控：`燃烧率 = 当前消耗 / 时间占比`。例：30 天窗口，10 天已消耗 50% 预算 → 燃烧率 = 0.5 / (10/30) = 1.5（超速）

### 第四步：告警策略（用燃烧率而不是裸阈值）

| 燃烧率 | 窗口 | 告警级别 | 动作 |
| ------ | ---- | -------- | ---- |
| ≥ 14.4 | 1h | Pager（立即） | 大概率已在违反 SLO，立即响应 |
| ≥ 6 | 6h | Pager（较急） | 高风险，尽快响应 |
| ≥ 3 | 24h | Ticket（当日） | 需关注，安排排查 |
| ≥ 1 | 3d | Ticket（本周） | 接近预算红线，规划可靠性工作 |
| < 1 | 长期 | 无 | 健康 |

告警必须可行动：每条告警标注影响、可能根因、初步排查命令，禁止"指标过高"式无信息告警。

### 第五步：SLO 治理闭环

- 每次事故复盘后更新：本次消耗了多少错误预算？剩余多少？按当前燃烧率何时耗尽？
- 每月回顾：SLO 是否还符合业务预期？告警是否有效（误报率 / 漏报率）？
- SLO 变更走决策记录：变更原因、影响、撤销条件（见 `architecture-decision.md`）

## 失败回退

| 失败类型 | 动作 |
| -------- | ---- |
| 无监控数据可复盘 | 如实标注"数据缺失"，行动项增加"补齐监控"，不虚构时间线 |
| SLI 无法采集 | 先用现有日志 / 指标近似，明确采集缺口并列入行动项 |
| 行动项无人认领 | 复盘不关闭，明确角色认领后再归档 |
| 错误预算计算口径不清 | 先统一窗口与分母口径，再出数字 |

与 SKILL.md「失败重试基线」冲突时，以基线为准。
