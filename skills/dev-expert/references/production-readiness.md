# 生产就绪审查与渐进式发布（Production Readiness Review & Progressive Delivery）

> **定位**：上线前的最后一道工程闸门——**PRR（生产就绪审查）**用检查清单逐项确认"这个系统能不能上生产"，**渐进式发布**用灰度 / 金丝雀 / 分批发布把上线风险降到可控。部署、发布、上线、灰度、回滚相关任务时加载，与 `software-project` / `website-project` 的发布运维步骤协同。
> **触发**："上线前检查"、"生产就绪"、"PRR"、"灰度发布"、"金丝雀"、"canary"、"分批发布"、"发布门禁"、"上线 checklist"、"回滚方案"。
> **铁律**：**没有回滚方案不上线**；**PRR 全绿是发布前提，有未通过项必须显式披露或阻断**；**渐进式发布不是可选项，是生产发布默认路径**。

## 第一部分：生产就绪审查（PRR）

### 第一步：按维度逐项检查

**可观测性**：

- [ ] 日志：关键路径有结构化日志（含请求 ID），日志级别可配置
- [ ] 指标：核心 SLI 已埋点（可用性 / 延迟 / 吞吐，见 `incident-review.md` SLO 部分）
- [ ] 告警：关键指标有可行动告警（含燃烧率告警），告警有初步排查指引
- [ ] 追踪：跨服务调用可追踪（trace ID 贯通）

**可靠性与回滚**：

- [ ] 回滚方案：明确回滚动作（回滚版本 / 数据库回滚 / 开关降级），已演练或步骤可执行
- [ ] 备份：数据备份策略就绪（全量 + 增量频率、恢复演练）
- [ ] 限流 / 熔断 / 降级：上游抖动时系统行为已定义
- [ ] 幂等：写操作幂等，重试安全

**容量与性能**：

- [ ] 容量评估：预期峰值流量 / 数据量的容量结论
- [ ] 性能基线：关键路径有基准（见 `performance-benchmark.md`），与目标 SLO 对齐
- [ ] 资源限制：连接池、队列、线程数有上限配置

**安全**：

- [ ] 安全基线：认证 / 授权 / 传输加密已核对（见 `threat-modeling.md`）
- [ ] 敏感信息：无密钥 / Token 硬编码或入日志，密钥走安全配置
- [ ] 依赖：依赖审计无未披露高危漏洞（见 `threat-modeling.md` 供应链部分）

**数据**：

- [ ] 数据迁移：迁移脚本可回滚，已验证
- [ ] 数据一致性：存量 / 增量数据处理有校验
- [ ] 数据保留 / 删除：符合隐私与合规要求

**流程**：

- [ ] 发布窗口与负责人已明确
- [ ] 变更单 / 发布记录已填写
- [ ] 干系人已知晓（值班、客服、上下游团队）

### 第二步：PRR 结论分级

| 结论 | 判定 | 动作 |
| ---- | ---- | ---- |
| 通过 | 全部必检项 ✅ | 可进入渐进式发布 |
| 条件通过 | 有非阻断项未满足（如低危优化项） | 列出条件与期限，条件满足前限制发布范围 |
| 阻断 | 有阻断项未满足（如无回滚方案、高危安全项） | 阻断发布，补齐后重新审查 |

**阻断项强制披露**：PRR 未通过即强行上线 = 跳过验证交付，交付判无效（见 SKILL.md「无证据 = 未完成」）。

### 第三步：PRR 报告模板

```
## PRR 报告

**发布对象**：[版本 / 提交 / 服务]
**审查时间 / 审查人**：
**逐项结论**：[可观测性 / 可靠性 / 容量 / 安全 / 数据 / 流程 各维度 ✅/❌/条件]
**阻断项**：[如无则写"无"]
**条件项**：[条件 + 期限]
**发布建议**：[通过 / 条件通过 / 阻断，附理由]
```

## 第二部分：渐进式发布

### 第一步：选择发布策略

| 策略 | 适用 | 特点 |
| ---- | ---- | ---- |
| 金丝雀（Canary） | 服务端发布 | 先 1%-5% 流量验证，逐步放量 |
| 灰度 / 分批（Rollout） | 大规模发布 | 按批次 / 用户组 / 区域放量，每批验证后放下一批 |
| 功能开关（Feature Flag） | 新旧逻辑共存 | 代码已上线但功能关闭，开关控制可见性，回滚最快 |
| 蓝绿 / 滚动 | 服务端发布 | 双环境切换 / 滚动替换，回滚 = 切回旧环境 |

**默认路径**：服务端发布走金丝雀或灰度；高危 / 大流量 / 数据变更发布必须分批。

### 第二步：发布门禁与放量节奏

- **门禁**：每批放量前核对——错误率不升、延迟不升、SLO 未消耗异常（见 `incident-review.md` 燃烧率）、无新增告警
- **放量节奏示例**：1%（观察 15min）→ 10%（观察 30min）→ 50%（观察 30min）→ 100%（观察 60min）
- **关键指标对比**：每批放量后与基线对比（错误率 / P95 延迟 / 成功率），异常即暂停放量
- **回滚触发条件**（任一命中即回滚，不等人工决策）：错误率超过阈值 N 倍 / SLO 预算快速消耗 / 用户反馈集中 / 数据异常

### 第三步：回滚执行

- 回滚动作要**预先写死**在发布计划里：回滚版本号、回滚命令、数据库回滚脚本、开关关闭方式
- 回滚后验证：确认已回到上一稳定版本，数据无残留损坏
- 回滚是正常发布流程的一部分，不视为"失败耻辱"；回滚后走复盘（见 `incident-review.md`）

### 第四步：发布后观察

- 发布完成不是终点：观察窗口内持续盯错误率 / 延迟 / 告警 / 用户反馈
- 观察窗口结束时更新发布记录：实际放量节奏、是否触发回滚、指标表现
- 发布后 24h 内出现异常走事故流程（`incident-review.md`）

## 输出模板

```
## 发布计划

**发布对象 / 版本**：
**策略**：[金丝雀 / 灰度 / 功能开关 / 蓝绿]
**放量节奏**：[各批次 + 观察时长]
**门禁指标**：[每批放量的通过标准]
**回滚方案**：[回滚版本 + 命令 / 脚本 + 触发条件]
**发布后观察**：[观察窗口 + 盯哪些指标]
**PRR 结论**：[引用 PRR 报告结论]
```

## 失败回退

| 失败类型 | 动作 |
| -------- | ---- |
| 无法实现金丝雀 / 灰度（架构限制） | 用功能开关或蓝绿替代；都不行则显式披露风险并缩小发布窗口 |
| 放量批次异常 | 暂停放量，先定位（`root-cause-debugging.md`），不跳批 |
| 回滚脚本未验证 | 视为阻断项，先演练再发布 |
| 发布后指标基线缺失 | 补基线后对比，未补前不得声称"发布无影响" |

与 SKILL.md「失败重试基线」冲突时，以基线为准。
