# 威胁建模与供应链安全（Threat Modeling & Supply Chain Security）

> **定位**：在开发阶段把安全前置——**威胁建模**（系统化识别"攻击者会怎么打进来"，在设计 / 改造前出威胁清单与缓解措施）与**供应链安全**（依赖引入前的审查、锁定与审计）。新系统设计、敏感功能改造、引入第三方依赖、安全审查（`code-review` 协同）时加载。
> **触发**："威胁建模"、"STRIDE"、"安全设计"、"攻击面"、"这个功能安全吗"、"依赖审计"、"供应链安全"、"SBOM"、"npm audit"、"composer audit"、"第三方库审查"。
> **铁律**：**威胁建模是设计活动不是合规填表**；**引入依赖前先审查，不是装上后再说**；**未缓解的高危威胁必须在交付中显式披露**。

## 第一部分：威胁建模

### 第一步：绘制数据流图（DFD）

先画系统 / 功能的数据流，再谈威胁。最小要素：

- **信任边界**：哪些区域可信（如服务端内部）、哪些不可信（如公网客户端、第三方回调）
- **处理节点**：服务、函数、存储
- **数据流**：数据从哪来、到哪去、经过哪些处理
- **存储**：数据库、缓存、文件、日志

只读信息查询 / 简单任务可画简化版（一条请求链路 + 信任边界）；复杂系统必须画出完整 DFD 再进第二步。

### 第二步：STRIDE 逐类过威胁

对每个数据流 / 节点，按 STRIDE 六类逐项问"会不会被打"：

| 类别 | 威胁 | 典型问题 | 常见缓解 |
| ---- | ---- | -------- | -------- |
| Spoofing 假冒 | 冒充身份 | 谁能冒充用户 / 服务 / 来源 IP？ | 认证、签名、来源校验 |
| Tampering 篡改 | 数据被改 | 数据在传输 / 存储中能否被篡改？ | 完整性校验、签名、防篡改存储 |
| Repudiation 抵赖 | 否认操作 | 能否否认做过某操作？ | 审计日志、签名、不可否认凭证 |
| Information Disclosure 泄露 | 数据泄露 | 敏感数据是否被越权读取 / 日志泄露？ | 最小权限、加密、脱敏、日志过滤 |
| Denial of Service 拒绝服务 | 服务不可用 | 能否被刷爆 / 打挂？ | 限流、配额、超时、容量规划 |
| Elevation of Privilege 提权 | 越权提权 | 低权限能否执行高权限操作？ | 权限校验、纵深防御、最小权限 |

**输出格式**（每个威胁一条）：

```
- 威胁: [编号 T1] [类别] [一句话描述]
  数据流位置: [哪个 DFD 元素]
  影响: [后果严重度 高/中/低]
  利用难度: [高/中/低]
  缓解: [对应措施 + 落在哪个环节]
  验证: [如何证明缓解有效]
```

### 第三步：威胁排序与缓解

- 按 `影响 × 利用难度` 排序，高危（影响高 + 难度低）优先缓解
- 缓解落到**具体代码 / 配置 / 流程**环节，不写空话（"做好安全防护"无效，"登录接口限流 5 次/分钟 + 验证码"有效）
- 每条缓解配验证方式：单测 / 代码审查 / 手动攻击测试 / 安全扫描
- **不可缓解 / 暂不缓解的高危威胁**：必须在交付中显式披露（见 SKILL.md「未验证项强制披露」）

### 第四步：与代码审查协同

- 威胁模型输出作为 `code-review` 的安全审查清单输入：审查时逐条核对缓解是否真实落地
- 发现缓解缺失 → 记为安全缺陷，按审查问题分级输出
- 常见 Web 威胁（XSS / CSRF / SQL 注入 / 越权）已有专项清单：CMS / PHP 见 `cms-development`，前端见 `frontend-design`，数据库见 `mysql-database`；本专项负责**系统级**（信任边界、提权链、DoS）与**新型攻击面**

## 第二部分：供应链安全

### 第一步：引入依赖前的审查门禁

引入新依赖前（npm / composer / pip / maven 等），先回答：

| 检查项 | 通过标准 |
| ------ | -------- |
| 必要性 | 能否用标准库 / 现有依赖实现？ |
| 来源 | 官方源？作者可信度？Star / 维护活跃度 / 最近发布时间？ |
| 许可证 | 许可证是否与项目兼容（MIT/Apache 通常宽松，GPL 需评估）？ |
| 已知漏洞 | 查官方公告 / 漏洞库，当前版本是否有未修复高危漏洞？ |
| 传递依赖 | 依赖树是否引入不必要 / 可疑的间接依赖？ |
| 安装脚本 | 安装过程是否有可疑的网络请求 / 代码执行？ |

**引入决策后**：锁定精确版本（`package-lock.json` / `composer.lock` / `pip freeze`），禁止浮动版本进入生产构建。

### 第二步：依赖审计（常态化）

| 生态 | 审计命令 | 频率 |
| ---- | -------- | ---- |
| Node.js | `npm audit` / `npm audit fix --dry-run` | 每次依赖变更 + 定期 |
| PHP / Composer | `composer audit` | 每次依赖变更 + 定期 |
| Python | `pip-audit` | 每次依赖变更 + 定期 |
| Java / Maven | `mvn dependency-check` / OWASP DC | 每次依赖变更 + 定期 |
| Go | `govulncheck` | 每次依赖变更 + 定期 |

审计发现高危漏洞：评估实际可达性（是否在攻击路径上）→ 优先升级修复 → 无法升级时记录为**已知限制**并在交付披露，不得静默忽略。

### 第三步：SBOM 与溯源

- 重要交付（对外发布、上生产）生成 SBOM（软件物料清单）：`syft` / `cyclonedx-bom` / `trivy` 等
- 关键依赖记录来源与版本锁定依据，便于漏洞公告后快速定位影响面
- 二进制 / 安装包签名校验：下载后核对官方校验和 / 签名，禁止信任未校验来源

### 第四步：CI/CD 供应链防线

- 构建流水线锁定依赖版本（lockfile 强制校验，禁止 lockfile 漂移）
- 流水线加入依赖审计步骤：高危漏洞失败门禁（fail build）或人工放行
- 最小权限：CI 凭证按需授予，不用万能 Token；第三方 Action / 插件审查后再接入（与 `code-review` 协同）

## 输出模板

```
## 威胁建模 / 供应链安全报告

**范围**：[系统 / 功能 / 数据流范围]
**信任边界**：[哪些区域可信 / 不可信]
**威胁清单**：[T1..Tn，含类别、位置、影响、难度、缓解、验证]
**高危未缓解项**：[显式披露 + 原因 + 建议动作]
**依赖审查结论**：[引入 / 拒绝 / 条件引入 + 依据]
**依赖审计结果**：[命令 + 输出摘要 + 处理动作]
**SBOM / 溯源**：[生成产物 / 锁定文件 / 签名校验结果]
```

## 失败回退

| 失败类型 | 动作 |
| -------- | ---- |
| 无法确定依赖来源可信度 | 标记"待人工评估"，不自动引入生产 |
| 漏洞无法修复且攻击路径可达 | 升级为高危未缓解项，交付中显式披露并给出缓解窗口 |
| 威胁缓解无法验证 | 标注验证方式缺失，列入审查关注项，不声称已缓解 |
| 审计工具不可用 | 用官方漏洞公告 / 依赖版本比对替代，说明工具缺口 |

与 SKILL.md「失败重试基线」冲突时，以基线为准。
